Programmable Protocol Emulator ASIC

Overview

This project implements digital communication protocols as programs running on a small dual-engine processor. The engines share a pin interface and a capture unit, while Python tools assemble programs, load memory, and compare execution with a reference model. The design was developed for the Jane Street Protocol Emulator ASIC Competition.

The principal change from V2 to V3 is the separation of instruction execution from output timing. V2 expresses timing through instruction delays; V3 allows an engine to schedule a transition against a shared clock, leaving a pin cell to apply the transition at the specified deadline.

Source repositoryDocumentation

V2 and V3

In V2, a firmware author must account for the number of cycles taken by the path leading to an output instruction. Conditional paths can therefore require different delay compensation. V3 assigns each engine a private time cursor and gives each pin a pending transition slot. Firmware advances the cursor by the desired interval; the pin cell applies the change when the shared timebase reaches that deadline, provided the engine schedules it in time.

Moving each program from flip-flops to SRAM also increases the available instruction storage. The wider instruction format and larger memory support the additional scheduling operations without making program storage a proportional collection of standard-cell registers.

V3 implementation

Execution and timing

Each engine reads a 32-bit instruction from its 256-word SRAM and maintains a private cursor on the shared 24-bit timebase. Output instructions schedule pin values or output enables, while timestamped input events provide a reference for receive operations. The host uses a 48-clock SPI frame to load and read back programs, service queues, and inspect status.

Protocol firmware

The UART transmitter uses 8N1 framing and takes bytes from the host transmit queue. Its data-dependent paths take nine or ten clocks per bit, but both advance the cursor by the same bit period. At 1 Mbaud, each bit occupies 48 core clocks, leaving time to prepare the next transition. The receiver places samples relative to the timestamp of the start edge, rather than estimating sample position from the instruction path.

The supplied programs include 115,200-baud UART examples, with the requested period rounded to representable clock intervals. The documented 1-Mbaud timing describes firmware operation; sustained transfers also require the host to service the queues. The FPGA result below establishes program execution and a captured digital output, not a measured 1-Mbaud UART loopback.

Verification

The programmable core is checked by comparing model and RTL execution, by observing its protocol pins with independent peers, and by proving selected control and queue properties with Yosys induction. These methods examine different aspects of the design: a matching architectural trace does not, by itself, establish the timing or framing of an external protocol.

The selected routed netlist passed 14 functional scenarios covering loading and readback, synchronized starts, queues, arbitration, filtering, capture, and status. The physical implementation passed nine prechecks. Extracted timing reports a slow-corner register setup margin of +2.58 ns and a fast-corner hold margin of +0.112 ns at a 20.83 ns clock period. These are tool-based physical-design results; fabricated-silicon operation has not been established.

FPGA implementation

The Artix-7 implementation runs on a Digilent Cmod A7-35T. A 12 MHz oscillator supplies a 48 MHz core clock, FPGA block RAM replaces the ASIC SRAM macros, and a USB-UART bridge carries host commands to the SPI interface. Program loading, readback, and execution were exercised on the board.

A Vivado ILA capture recorded a 25 kHz output with 960 core-clock samples per half-cycle, corresponding to 20 µs at 48 MHz. The capture observes internal digital signals and establishes the timing of this programmed output; it does not measure analog signal quality or demonstrate every protocol configuration.

Physical layout

The two SRAM macros lie along the lower edge of the 1,724 × 711 µm die, with their signal pins facing the standard-cell logic above them. The viewer retains both the overview and original polygon geometry so that the placement and routing can be examined at different scales.

V2 implementation

Execution model

V2 established the dual-engine design, with separate 64-word programs, transmit and receive queues, and a shared 32-record capture unit. Both engines run at 25 MHz, and firmware uses instruction delays to establish protocol timing. Pin ownership prevents the engines from driving the same output, while synchronized inputs and optional filtering support reception.

The UART verification includes sustained full-duplex simulation at 115,200 baud and preloaded 16-byte full-duplex bursts at 1 Mbaud. The higher wire rate is a burst capability in those tests; it should not be interpreted as a demonstrated continuous host-to-wire throughput. The released examples also cover both SPI roles and I²C at 100 and 400 kHz.

Physical result

The selected V2 physical implementation was validated through a local Tiny Tapeout checkpoint recovery. Its elaborated RTL and prepared settings correspond to the released software. Extracted timing passed at all three reported corners, with a lowest setup margin of +18.46 ns and lowest hold margin of +0.054 ns. The retained results include nine physical prechecks and 14 functional gate-level scenarios.

These results describe the recovered physical-design run and functional simulation. They do not establish fabricated-silicon operation, FPGA operation of V2, or competition acceptance.

Physical layout

The V2 layout occupies a 6 × 4 tile allocation and stores program instructions in standard-cell registers. Comparing it with the two SRAM macros in V3 makes the program-memory change visible in the physical implementation.
